## 1. Project Overview

RustMSPT (Rust Microstructure Processing Toolbox) is a standalone Rust toolkit for STL-based microstructure processing. It provides end-to-end pipelines for splitting, packing, optimizing, forging, scaling, measuring, and cropping microstructural geometries.

`PLAN.md` tracks implementation progress for portable GPU acceleration and target-aware packing. Feature-gated `wgpu` paths coexist with CPU `rayon`/`rustfft`/`parry3d-f64` reference implementations and CPU fallback.

The codebase has a full documentation tree under `docs/en-us/` (conceptual algorithm docs, per-function reference docs, and captured-output pipeline walkthroughs). See [Documentation Map](#2-documentation-map) below for how it's organized and, critically, the order in which it must be consulted.

## 3. Algorithm Overview

One subsection per file in `docs/en-us/algorithms/`. These are high-level summaries only — read the linked full doc before implementing or debugging anything in the area.

### S2 Two-Point Correlation

S2(r) is the probability that two points a distance `r` apart both land in solid particle material; at `r=0` it equals volume fraction, decaying toward VF² as `r` grows for a random medium. Every CPU method reduces to a ray-casting point-in-mesh test (Möller–Trumbore, fixed non-axis-aligned ray direction, hit-distance deduplication within `1e-8`), and `calculate_s2` dispatches between three strategies — direct mesh Monte Carlo, voxelized Monte Carlo, and exact FFT-autocorrelation or direct shell-pair enumeration (chosen by a 24,000,000-cell padded-grid-size threshold). GPU counterparts mirror all three via wgpu compute kernels and fall back to the CPU path on GPU init failure. It powers `measure` (S2 reported as a diagnostic, exact-vs-Monte-Carlo comparison via `l2_norm`) and `optimize` (S2 L2 distance to a target curve as the simulated-annealing loss function). [Full doc](docs/en-us/algorithms/s2-two-point-correlation.md)

### Simulated Annealing and the Island Model

`OptimizePipeline` rearranges a loaded particle assembly's positions/orientations so its S2 curve matches a target curve, using simulated annealing: random perturbations (60% local translate/rotate, 30% move-toward-neighbor, 10% full random reposition) are accepted via the Metropolis criterion, with adaptive temperature nudging to keep the acceptance rate inside a `[0.20, 0.45]` target band. Before SA starts, `selective_prune_to_target_vf` cheaply thins the particle set toward the target volume fraction so SA doesn't spend its budget removing particles one accept/reject decision at a time. When `optimization.islands > 1`, multiple independent SA searches run in parallel threads, each keeping its own temperature/cooling state, periodically migrating the better of "mine vs. global best" through a shared `Arc<Mutex<GlobalBest>>`. It powers the `optimize` pipeline end to end (`run_sa_island`, `selective_prune_to_target_vf`, `OptimizePipeline::run`). [Full doc](docs/en-us/algorithms/simulated-annealing-island-model.md)

### FFD Forging

Forging in RustMSPT is a closed-form kinematic approximation of axial-compression forging — no material model, plasticity, stress/strain field, or FEA — implemented as a per-vertex affine scaling around a chosen center point, with an extra radial-scaling pass for "void" meshes. `simulate_forging_ffd_with_tracking` generalizes this with a configurable compression axis, a deformation center taken from a caller-supplied lattice bbox (not the mesh's own bbox), void densification (extra centroid-ward pull modeling pore collapse), and optional region-of-interest bounding-box tracking through the same transform. `bulge_factor` interpolates the lateral scale between "no bulge" (height only shrinks) and "volume-conserving bulge." It powers the `forge` pipeline (`ForgePipeline::run`), which also reports volume fraction inside the ROI before/after compression. [Full doc](docs/en-us/algorithms/ffd-forging.md)

### Mesh Rendering (CPU Ray Casting and GPU Offscreen Rasterization)

The `render` pipeline turns an STL mesh into an RGBA image from a configured viewpoint. The camera is defined by a focus point (the image-center target) and a view direction (from the camera toward the focus), with an optional up vector (default `[0,0,1]`, automatic fallback when nearly parallel to the view direction) and auto-fitted framing from the mesh bounding box: orthographic mode fits the bbox extents in the camera plane (aspect-corrected), perspective mode places the camera so the bbox bounding sphere fits the vertical FOV. The CPU path (`render_mesh_cpu`) casts one ray per pixel through parry3d's QBVH-backed `TriMesh::cast_local_ray_and_get_normal` (nearest hit, two-sided Lambert headlight shading), parallelized over rows with rayon; the feature-gated GPU path (`GpuRenderPipeline`) rasterizes expanded triangles to an offscreen `Rgba8Unorm` texture with a `Depth32Float` buffer — no window or surface — and reads pixels back through a 256-byte-aligned staging buffer. Both paths share `RenderCamera`/`RenderSettings` so their outputs match within ~1 LSB per channel and ~1px at triangle edges; GPU failures fall back to CPU. [Full doc](docs/en-us/algorithms/stl-rendering.md)

### Packing Target Diameter Distribution

Standard sequential packing has no control over the size distribution of particles it places; this feature adds that control by steering accepted candidates toward under-represented bins of a user-supplied diameter histogram (e.g. `data/input/gu2019_fig7b_pore_distribution.csv`) while keeping target volume fraction as the primary objective. `TargetDistribution::choose_bin` picks the bin with the largest positive "debt" (`frequency × next_count − observed_count`), falling back to a total-variation-distance-minimizing choice when no bin is under-represented; candidates are rescaled to a bin's midpoint diameter via `scale_mesh_to_equivalent_diameter` and re-checked against geometry filters, with up to `TARGET_BIN_PROBES = 4` retries per bin before the algorithm falls back to whatever bin can currently accept a particle. An independent, optional soft control (`SphericityState`) steers the running mean sphericity toward a target band without ever rejecting a candidate solely for its sphericity. It powers the `pack` pipeline's target-steering path (`PackPipeline::run` + the `src/pipeline/pack_targets.rs` engine). [Full doc](docs/en-us/algorithms/packing-target-diameter-distribution.md)

### PCA Volume Alignment and Crop

Raw CT reconstructions are never aligned to the scan axes, so a naive axis-aligned crop either wastes volume or clips the sample. The `crop` pipeline fixes this by detecting background from the volume's outer boundary shell (`detect_background_mode`), running PCA on the foreground voxel point cloud's covariance matrix (`nalgebra::SymmetricEigen`, sorted eigenvectors forced into a right-handed frame) to find the sample's natural orientation, then inverse-mapping every output voxel back into the original volume to resample it (nearest or trilinear interpolation) into a new axis-aligned, tightly-cropped frame — on CPU via rayon `par_chunks_mut` over z-slices, or on GPU (feature-gated) above a 100,000-voxel output threshold, falling back to CPU on GPU failure. A final heuristic pass trims stray reconstruction-artifact voxels off the XY border. It powers the `crop` pipeline (`CropPipeline::run`, `estimate_pca_bbox`, `rotate_and_crop`/`rotate_and_crop_gpu`). [Full doc](docs/en-us/algorithms/pca-volume-alignment-crop.md)

### Spatial Grid Collision Detection

Brute-force pairwise mesh collision checking is `O(N)` per candidate and `O(N²)` per full pass, dominated by expensive `parry3d` triangle-mesh queries. `SpatialGrid` (`src/geometry/spatial.rs`) is a uniform bucket grid sized to the largest particle's bounding-box extent, giving `O(k)` neighbor queries instead; exact resolution then layers an AABB reject before falling back to `parry3d`-backed intersection/distance tests, and `generate_periodic_ghosts` handles boundary-mode-3 wraparound by checking a candidate against up to 26 shifted copies of neighboring particles. The two consumers differ: `optimize`'s `run_sa_island` builds and repeatedly rebuilds a `SpatialGrid` (its intended use case — many queries against a population whose positions keep changing), while `pack`'s `PackPipeline::run` deliberately skips the grid and instead does a rayon-parallelized brute-force scan over the `placed` list, since packing only ever checks each newly placed particle once. [Full doc](docs/en-us/algorithms/spatial-grid-collision.md)

### Mesh Clipping and Volume-Fraction Accounting

Volume-fraction accounting needs the volume of each particle mesh restricted to the packing box (not its total volume), since particles are allowed to straddle a domain boundary under modes 2/3 — and the clipped result must stay watertight for the divergence-theorem volume formula to be meaningful. `src/geometry/volume.rs` implements a Sutherland-Hodgman single-plane clipper that re-caps the hole it cuts (via cross-plane segment extraction and fan-triangulation of the resulting ring), a six-plane box clip built from that primitive, and quantized-key vertex deduplication (`(x * 1e6).round()`) to merge coincident cap vertices. This VF computation (`particle_volume_in_bbox`, `volume_fraction_of_meshes_in_bbox`) is the shared core metric that packing, optimization, and measurement pipelines all build on. [Full doc](docs/en-us/algorithms/mesh-clipping-volume-fraction.md)

## 4. Build & Run

```bash
export PATH="$HOME/.cargo/bin:$PATH"

# Debug build
cargo build

# Release build (recommended for real data)
cargo build --release

# Run a pipeline
cargo run --release -- <subcommand> [--config <path>] [--input <path>] [--output <path>]
./target/release/rustmspt <subcommand> --config data/input/<subcommand>_config.yaml
```

Available subcommands: `split-filter`, `pack`, `optimize`, `measure`, `forge`, `scale`, `crop`, `render`, `mesh-render`, `mesh-verify`, `mesh`


Environment variables for GPU selection:
- `RUSTMSPT_GPU_DEVICE=<name or index>` — filter adapter by name substring or index
- `RUSTMSPT_ACCELERATION=cpu|gpu|auto` — override config acceleration mode

### 3. Data Pipeline Validation (requires `data/input/` files)

Pipelines must be run in dependency order (pack depends on split-filter output; optimize depends on pack output; measure/forge/scale depend on optimize output):

```bash
./target/release/rustmspt split-filter --config data/input/split_filter_config.yaml
./target/release/rustmspt pack --config data/input/pack_config.yaml
./target/release/rustmspt optimize --config data/input/optimize_config.yaml
./target/release/rustmspt measure --config data/input/measure_config.yaml
./target/release/rustmspt forge --config data/input/forge_config.yaml
./target/release/rustmspt scale --config data/input/scale_config.yaml
./target/release/rustmspt crop --config data/input/crop_config.yaml
./target/release/rustmspt render --config data/input/render_config.yaml
```

After running, verify key outputs:
- `data/output/s2_history.txt` must contain entries: `Pruning Start:`, `Pruning Round`, `Pruning Completed:`, `Post-Pruning S2:`, `Final Best S2:`
- `data/output/measured_s2.txt` must have non-zero exact S2 values
- `data/output/rendered.png` must be a valid PNG with visible shaded particles on the background

## 8. Code Conventions

- No comments in code unless explicitly requested.
- **AI-FUNC-SUMMARY comments are the exception**: every function must have an `AI-FUNC-SUMMARY` comment (see [Function Reading Policy](#9-function-reading-policy-for-ai-agents) below).
- Program comments, configuration-file comments, and all `AI-FUNC-SUMMARY` text must be written in English.
- Follow existing patterns: use `crate::types::{Mesh, Vec3, BoundingBox}` for core types.
- Geometry functions live in `src/geometry/`, pipeline logic in `src/pipeline/`, config in `src/config/`.
- Public API is re-exported through `mod.rs` files in each module.
- Error handling uses `crate::error::{Result, RustMsptError}`.
- All new parallel code must use rayon and be safe for concurrent access (no data races on mutable state).
- Config fields use `serde` deserialization with optional `deserialize_with` for flexible numeric parsing.
- **Every code modification must update `AGENTS.md`** to reflect any changes to architecture, file structure, testing steps, conventions, or pitfalls.
- **If `PLAN.md` exists, every code modification must also update `PLAN.md`** to reflect current progress, decisions, and next steps.
- GPU-related changes must keep CPU fallback behavior intact and update `PLAN.md` with implementation progress, test coverage, and any changed architectural decisions.
- **Every code modification must also update the corresponding documentation under `docs/en-us/`** (and mirror the change into the corresponding `docs/zh-cn/` file per `docs/TRANSLATION_GUIDE.md`, or flag it there as pending translation if a full translation isn't feasible in the same change): update the function's entry in the matching `docs/en-us/reference/*.md` file (signature, purpose, params, returns, side effects, notes) whenever its behavior, signature, or `AI-FUNC-SUMMARY` changes; add a new entry and a `function-index.md` row for every new function; remove entries for deleted functions; update the relevant `docs/en-us/algorithms/*.md` file when algorithmic behavior changes; and update the relevant `docs/en-us/examples/*.md` file when CLI flags, config fields, or example output change.

## 9. Function Reading Policy for AI Agents

This section describes practice at **reading-order level 3** (specific function implementation) from the [Documentation Map](#2-documentation-map) above: it applies once you've descended past levels 1–2 because the algorithm docs and reference docs weren't enough, and you're now reading or navigating Rust source directly. Within source, this codebase uses `AI-FUNC-SUMMARY` comments as a lightweight semantic index for functions — the bridge between level 2 (`docs/en-us/reference/*.md`) and level 3 (the function body itself). These comments appear immediately above each function definition (or inside the existing docstring for Rust `///` style where already established) and follow one of two formats:

**Full format** (for non-trivial functions):
```
// AI-FUNC-SUMMARY:
// Purpose: <one short sentence describing what this function is responsible for>
// Inputs: <important parameters only; omit obvious ones if trivial>
// Returns: <what the caller receives, or "None">
// Side effects: <state changes, file/network/database/UI effects, logging, mutation, or "None">
// Notes: <important assumptions, edge cases, invariants, or when the function should be used; omit if unnecessary>
```

**Compact one-line format** (for very small/trivial functions):
```
// AI-FUNC-SUMMARY: <short purpose>; returns <result>; side effects: <none or brief description>.
```

When inspecting code:
1. Read the file-level structure, function names, signatures, and `AI-FUNC-SUMMARY` comments first.
2. Do not read entire function bodies unless the summary/signature is insufficient, the function is directly relevant to the requested change, or debugging requires implementation details.
3. Treat summaries as navigation aids, not as a substitute for source code when making behavior-changing edits.
4. When modifying a function, update its `AI-FUNC-SUMMARY` if the purpose, inputs, return value, side effects, assumptions, or error behavior changed.
5. When adding a new function, add an `AI-FUNC-SUMMARY` comment at the same time.
6. If a summary appears stale or inconsistent with the implementation, correct the summary before relying on it.
7. `AI-FUNC-SUMMARY` comments and `docs/en-us/reference/*.md` entries must stay in sync: when you update a function's `AI-FUNC-SUMMARY`, update its corresponding entry in the matching `docs/en-us/reference/*.md` file (and its `function-index.md` row) in the same change.

## 10. Common Pitfalls

- `ThreadPool` is not `Clone`. Use references or create separate pools per island.
- `parry3d::TriMesh::new()` can return `Err` for degenerate meshes; always handle with `Option`.
- `rustfft::Fft` is `Send + Sync` but not `Clone`. For parallel FFT, each thread creates its own `FftPlanner`.
- `Volume3D.data` stores voxel values as `i64`. The `numeric_type` field tracks original bit depth.
- `split_mesh_into_granules` returns an owned `Vec<Mesh>`; each granule is a connected component.
- SA optimization state (temperature, acceptance window) is per-island; do not share mutable SA state across threads.
- wgpu's `enumerate_adapters()` returns a `Vec`, not an iterator — do not call `.collect()` on it.
- `wgpu::Limits::max_storage_buffer_binding_size` is `u32`; cast to `u64` when comparing with `BackendCaps`.
- When `gpu` feature is disabled, `ComputeBackend::Gpu` variant does not exist — use `#[cfg(feature = "gpu")]` guards in match arms and `is_gpu()` instead of `matches!`.
- The `acceleration` config field uses `#[serde(default)]` so existing YAML configs without it continue to work. Tests constructing config structs manually must include `acceleration: Default::default()`.
- `Volume3D` uses z-major indexing: `idx = z * width * height + y * width + x`. GPU shaders must match this layout, not x-major.
- Equivalent-volume diameter and sphericity require a closed mesh with positive finite volume and surface area; malformed/open candidates are skipped when target controls are active.
- Packing diameter frequencies are count frequencies over successfully placed full components, not volume-weighted frequencies. Failed placement attempts must never update bin or sphericity state.
- Tests constructing `PackingParams` directly must include `target_diameter_distribution_csv`, `target_mean_sphericity`, and `mean_sphericity_tolerance`.
- `RenderedImage.rgba` is top-row-first RGBA8 and must contain exactly `width * height * 4` bytes.
- wgpu texture readback rows must be padded to `COPY_BYTES_PER_ROW_ALIGNMENT` (256 bytes) and unpadded before PNG encoding.
- CPU/GPU render tests must use tolerance at triangle edges; parry3d uses f64 QBVH ray casting while wgpu rasterization uses f32.
- `io/vtu.rs` appended-raw arrays must be collected in EMISSION order (FieldData, Points, Cells, PointData, CellData) — appended offsets are assigned by a running index during tag emission; any order mismatch corrupts every offset after the first out-of-order array.
- The contract `cell_kind` cell array (0 tet / 1 face / 2 curve / 3 voxel) is distinct from VTK cell type codes (10/5/4/11); `SceneFilter::CellKind` filters on the semantic array, falling back to mapping VTK types only when the array is absent.
- `build_scene` frames the camera from the FULL document bbox, not the filtered subset — deliberate, so all views/filters of one input frame identically.
- `mesh-render` uses the CPU path as the transparency reference (exact all-hits compositing); the GPU preview path (PLAN GA-3c, done) is opaque-only and selected via `backend: gpu | auto`. Scene transparency needs all-hits enumeration (`RayIntersectionsVisitor` over `TriMesh::qbvh()`); `cast_local_ray_and_get_normal` returns only the nearest hit.
- GPU scene triangles use `LessEqual` depth comparison because Volume boundaries are uploaded before tagged Face cells; this preserves the CPU Face-over-Volume rule for coincident geometry. GA-5 CPU baselines allow 2% of pixels beyond 2 LSB; full-fixture GPU comparisons allow 5% because line-overlay rasterization differs at edges.
- GA-5 render baselines must only be regenerated deliberately with `RUSTMSPT_UPDATE_RENDER_BASELINES=1 cargo test --test mesh_visual_regression_tests`; normal test runs compare without rewriting committed PNGs. Human visual inspection remains required for multimodal signoff.
- `build_scene` sorts hash-map-backed boundary faces and wireframe edges before emission; keep this ordering deterministic because transparent PNG baselines are sensitive to equal-depth traversal order.
- `mesh` normalizes by the configured domain diagonal before S0, runs S0 + S1 + G2-1..G2-5 + S3 + S4 + S5 + S6 + S7 + S8, then returns `Err(NotAvailable)` for S9..S11. The `s02_arranged` snapshot is emitted after box clipping and topology rebuild are complete; `s03_gapfield` follows S3, `s04_sizing` follows S4, `s05_lattice` follows S5, `s06_classified` follows S6, `s07_snapped` follows S7 and `s08_cut` follows S8. `snapshots: key` is exactly `{s02,s05,s08,s11}`; S0/S1/S3/S4/S6/S7 snapshots emit under `all`, s02/s05/s08 emit under `key` and `all`.
- **An ordering key must separate the nodes it orders — the weld grid does not.** S7's crossings are constructed points and are not welded against each other, so two can share a `NodeKey`; Rule SNK's "smallest key" then stops being a total order and two cells split a shared quad on opposite diagonals. S8 builds its key on `1e-6 × the weld quantum` (`KEY_ORDER_REFINEMENT`, SPEC §1.2 Rule K-O). Do **not** "fix" a key collision by welding the pair: that also merges crossings on different edges and collapses the cells between them.
- **S8 triages on the crossings, not on the ownership record.** A cell whose edges carry cut nodes from two components is a junction cell even when S6 records only one of them as ambiguous there. The cut tables read *cut nodes*; triaging on the record let one cell split a shared face with its own component's nodes while its neighbour used both, which puts a pair of single-sided faces at that spot.
- **`[V3]`'s boundary-leak rule measures against the octree hull, not the domain box**, whenever the lattice overhangs the box — which it always does, by up to one coarse cell per axis. Do not weaken this to "anywhere beyond the domain plane": that also swallows a detached component outside the box, which is a genuine defect.
- **A face two walls cross is walked along the edge, not by node id.** `face_states` inserts a face's cut nodes into its boundary loop; when two components each cut the same edge, the two nodes must be ordered by distance along that edge. Sorting them by node id is still *conforming* (both cells sort the same way) but walks the boundary backwards over that stretch, and everything built on the loop inherits it — that one line was worth 4,853 → 27 hanging nodes on the reference dataset.
- **G7-1's doubly-cut face rule runs per face, in every escalated cell** — never only inside the cells its cell-level split covers. A face two walls cross is shared by two cells and only one may be a sandwich; running the rule per cell makes them disagree and puts hanging nodes exactly where the gap is.
- **`regime` in the VTU is load-bearing, not decoration.** `[V7]`'s one-layer check reads it, and a band element's wall nodes must be nodes of a *tagged* face — so S8b tags the gap slab's two lids into the interface index. Writing `regime` as zeros (as `cut_to_doc` originally did) makes `[V7]` PASS vacuously on real output.
- **Rim collapse belongs at the *cut node*, not at the element.** G7-2 collapses a gap by giving a lattice edge whose two wall crossings are within `t_sheet` a **single shared cut-node id**, so no cell ever sees the gap and every face over it takes an ordinary §5.2 row. Welding the two walls after the cells are meshed looks equivalent and is not: the walls have by then triangulated their shared faces as a doubly-cut pair, every neighbour that split the same face once disagrees, and it cost 27,336 hanging nodes. Do not "simplify" this into a post-pass.
- **A check that reads an array its producer never fills passes by measuring nothing.** This has now bitten three times in `s08`: `regime` written as all-zeros made `[V7]`'s one-layer check vacuous, and `FaceTagKind` hard-coded to `0` made *both* `[V7]`'s sheet metrics and `[V8]`'s pinhole check vacuous — all three were green for years of fixtures. When you add a check, assert its input is non-trivial on at least one fixture. The same trap reappears when you *satisfy* a check: `[V8]` wants a sheet's boundary edges to be declared curves, and declaring all of them would have silenced it, so `collapsed_sheet_rim` derives the rim from the collapse decision instead and a pinhole still fails.
- **Measure the premise before building on it.** The open-sheet rim was filed as "S7 must intersect the arranged rim curves with the lattice to produce `split_R`'s `r`" — a substantial piece of geometry. Measuring first showed S7 already snaps nodes onto rim curves and the cut front already lands on the rim (19 of 22 boundary-edge midpoints exactly on it); the entire defect was that `cut_to_doc` declared no curve. The fix was a membership test, not a mesher. `split_R` stays implemented and unexercised, which is correct, not a gap.
- **"Two components on this face" is not "two patches on this face".** After a G7-2 rim collapse both walls of a gap cross the same edges at the *same node ids*, so a collapsed face carries two components and is an ordinary single-patch §5.2 face. `face_states` counted components and cost 1,152 boundary leaks; `face_is_single_patch` compares what each component contributes per edge. Any new "is this face simple" test must do the same.
- **A band cell's conformity comes from the *pair*, not from the cell.** `thin.rs` stores the rim collapse on the matched vertex pair, so a pair collapsed in one cell is collapsed in every cell that references it and neighbouring cells with different `k` agree on their shared quads with no negotiation (SPEC §8.1 Invariant B1). The one thing that is *not* a pure function of the quad is the §4.4 diagonal flip, so `mesh_band_layer` proposes it for both incident cells at once and accepts only if both still mesh — never per cell.
- **An escalated cell in S8 is not a skipped cell.** Its neighbours have split the faces they share with it, so emitting it whole puts hanging nodes in the mesh (4,577 of them on the review scene). Every escalation goes through `junction.rs`'s conforming fan: face triangulation is a pure function of the face's state, the interior is a centroid fan, and the face-centroid Steiner point is allocated **once per face** and shared by both incident cells.
- **`[V4]` warns after S8 and that is S9's budget, not a defect.** Cutting produces slivers by construction (`SPEC_meshgen_geometry.md` §6 states the expected distribution). Do not tighten S8 to chase it.
- `SPEC_meshgen_geometry.md` §4.3 gives prism **node lists** under "emit under the canonical orientation fix" — row 6 is negatively oriented on a plain straight prism. Emitting the table verbatim ships inverted elements; always go through `orient_positively`.
- S7 (snap) captures **corners and feature curves** within `0.3 * L_min`, but takes a **surface** target only where a crossing already sits within 2.5 % of a node (the re-check band) or within the weld tolerance of it (invariant K2). Capturing surfaces at the full cap radius consumes the cut: on a sphere at `h = 0.25` it took 74 crossed edges to 2. Do not "strengthen" the snap by widening that rule.
- `ArrangedSurface::corner_nodes` is **not** the sharp-corner set: S2 unions S1's corners and junctions with every point-feature node, and C6 fires for ordinary same-component vertex adjacency (2688 events over a 266-vertex sphere whose S1 corner count is 0). Any consumer wanting real corners must filter single-component point features, as `snap.rs` does.
- **This is an immersed-boundary mesher: nothing conforms to the geometry until S8.** S5's lattice is a background grid built without looking at the input, S6 staircases the shape to one element, and S7 (snap) + S8 (cut) are what make the boundary exact. A coarse-looking s05/s06 render is the design. Say so when reporting them rather than letting it read as a defect.
- Every S3 quantity is computed in the normalized frame (domain diagonal = 1); the pipeline multiplies `t_r`, `t_sheet`, `t_layer`, and the emitted `separation_t` by the domain diagonal before printing or writing. Do not compare a raw `GapField` value against a model-unit length.
- S3 emits one vertex sample per **smooth patch** at a vertex (incident faces clustered by normal agreement within `feature_angle_deg`), not one per vertex. A single averaged normal at a sharp vertex points into no wall, sends the ray out through a side face, and fails battery check 5; `build_adjacency` and check 5 must look the sample up by the face's own cluster.
- S3 samples **both sides** of every surface (the reference mesher samples only the calibrated inward side): a thin region may be material (`intra(X)`) or void (`inter(X_a,X_b)`), and R-B1 must decide about both. Closed-solid outward orientation comes from the sign of the component's own signed volume - S0 makes winding consistent within a patch but does not fix its global sign.
- The S3 closest-pair sweep skips triangle pairs sharing an arranged node (post-corefinement contacts, not gaps) and requires **same-component** pairs to face each other; without that a curved patch reports its own tessellation spacing as a gap. One seed is kept per `(triangle, opposite component)`.
- Battery check 1 accepts any sample of the opposite wall within `0.5*h` of `q` that measures the same separation and pairs back, not only the nearest one - coincident closest-pair seeds make "nearest" ambiguous. A check that cannot apply to a sample is cleared from `applicable`, never silently passed.
- S3 thin regions own **both** walls of a gap (reference pairing closure): a sample belongs to at most one region across every group, so one gap yields one region and one mid-surface, not two mirror copies. `ThinRegion.faces` is wall A (rims + mid-surface are built on it); `opposite_faces` is the wall pulled in by the closure.
- The S3 closest-pair sweep needs two extra rules beyond "within t_layer": same-component pairs must face each other within **25 degrees** (`COS_OPPOSING_INTRA`), not the 60-degree ray cone, and must be geodesically far (`geodesic_min_ratio`, bounded Dijkstra over face adjacency). Without the first, every convex edge reports the wedge of material inside it as a gap; without the second, a folded-over neighbourhood does. Cross-component pairs keep the 60-degree cone - the T-junction edge-to-face case has `|d.n| = 0` against the wall.
- A `Band` region admits a sample only when its **frozen** separation (`t_exact` if measured, else `t_raw` - the quantity that becomes `t_r`) is above `1.1 * t_sheet`, and the pairing closure applies the same floor. Growth connectivity still uses the smoothed field. Without this a single region spans from below `t_sheet` to `t_layer`, which no band template can mesh.
- Contacts are not gaps: `reject_geodesic_shortcuts` clears ray *and* sweep correspondences whose triangles are close along the surface (face adjacency spans components, because corefinement makes intersecting surfaces share edges). Both sets are keyed by component pair; never make them global or one contact will disqualify unrelated gaps. A geodesic ratio alone cannot do this job: around a shallow crossing the surface detour is as long as a real thin wall's.
- **Touching the contact set is necessary for `IntersectionWedge` and nowhere near sufficient, and taking it alone shut the whole thin path.** On a limb attached to a block every triangle of the limb is incident to the root curve, so the limb's own uniform gap was declared the curve's neighbourhood and all 19 regions of the sheet fixture were skipped. What makes a wedge a wedge is that the gap **closes**: `region_reaches_contact` now also requires `t_r < t_sheet < t_max`, so a region straddles the threshold - one end to be collapsed, the other meshed, and no single template doing both. Measured: every skipped region reported `t_r ~= t_max`, i.e. a uniform gap, not a wedge.
- **A uniform gap is the canonical sheet, and the gradient-only densifier could not see it.** `densify` refined where `|grad t|` was steep, which describes a *varying* gap well and a constant one not at all: a plate modelled as a box carries two samples per wall, the gradient between them is zero, no round fires, and the region then dies on the speck floor. The second criterion is spatial and confined to the thin band - a gap the field will resolve at `h_bootstrap` must be measured at `h_bootstrap`. Sheet fixture: 7 densified samples -> 148, and the limb's wall became one region of 128 samples with `area` exactly its 0.27x0.20.
- **Battery check 3 judges a sample against its own neighbourhood, never by veto.** Marking both ends of a discontinuous pair failed reads as symmetry and is not - the discontinuity has one author. At a plate's rim a sample's ray leaves the gap and lands on a far body, and under the veto that single outlier condemned all eight interior neighbours: 80 vetoes from a handful of rim samples took the region's confidence to 0.82 against a 0.90 gate. A majority test (`disagree > agree`) makes the outlier fail alone; confidence went 0.820 -> 0.992.
- **The mid-surface may not be built from vertex samples alone.** At a box plate's corner the vertex normal is the diagonal of three faces, so the ray leaves the gap instead of crossing it and every corner goes unpaired - four nodes, none usable, `MidSurfaceUnbuildable` for exactly the shape the mid-surface exists to describe. Nodes without a vertex sample are placed by the nearest measurement on the same wall (ties by earlier sample, for R-P2), which is the definition of a mid-surface: wall A carried half the local gap inward.
- **One gap must be one region, and the hysteresis walk alone does not deliver it.** The pairing closure claims the opposite wall's samples as it goes, so a later seed on the same wall finds them in its way and becomes an island. The band plate fixture came out as one region of 212 samples plus **21 fragments of one or two**. Regions of the same group and declared regime that touch are unioned after segmentation (undirected relation, re-indexed by lowest member, so it is order-independent).
- **`Speck` is an *area* test; sample count is `Undersampled`, and both suppress LFS.** A one-sample fragment beside a converted band region is a piece of that same gap, and letting it ask for `t / gap_cells` puts two elements across a gap the band conversion has undertaken to mesh with one - 340,360 LFS sources and a ten-fold mesh on a7b. A measurement too sparse for S3 to act on is too sparse to bind the field to its floor. `LowConfidence` and `MidSurfaceInvalid` are still *not* suppressed: those are real gaps the thin path failed to take.
- `bounded_geodesic` is capped at `GEODESIC_MAX_VISITS` faces and short-circuited by a face-adjacency connected-patch check; a shortcut path is short by definition, so the cap only ever answers "far", which is the safe direction.
- **R-P1: every mesh-generation stage must land parallel** (PLAN §12.5). The permitted shape is per-item work collected into an indexed buffer and concatenated in index order (`par_iter().map(...).collect()`, or `par_iter_mut` over disjoint slots). Forbidden: `par_iter().sum()` over floats, `Mutex<Vec<_>>` accumulation, HashMap iteration feeding a committed decision, early-exit races. A per-thread memo (`map_init`) is fine when the memo is pure.
- **R-P2: verify it.** Two runs at different `RAYON_NUM_THREADS` must produce byte-identical VTUs; that is the acceptance for any new parallel stage. Where an order-dependent step survives (e.g. `explicit_pairs` suppression in `validate_arrangement`), evaluate in parallel and apply the order-dependent part in a cheap serial pass afterwards.
- Allocation can eat the whole speedup: `TriGrid::query` allocating per call made the S3 sweep scale 1.0x on 8 threads (8 threads, 5.3 CPU-s, same wall time). `query_into` with a `map_init` per-thread buffer took it to 3.7x. Suspect the allocator before the algorithm when a parallel loop refuses to scale.
- `RUSTMSPT_TIME_STAGES=1` prints `[STAGE-TIME]` (pipeline), `[S2-TIME]` (arrangement) and `[S3-TIME]` (gap field) wall times.
- Three O(n^2) traps fixed in G3-5, all worth recognising elsewhere: a per-face loop calling a per-component full scan (`sorted_components`), per-triangle rescans of the whole registry (`split_all_triangles`), and a per-point-feature scan of every face (`validate_arrangement`). Two more: `BTreeMap::entry().or_insert(v)` evaluates `v` eagerly (use `or_insert_with`, or hoist the work), and per-item full rescans of the registry (`split_all_triangles`) must be replaced by an index built once in canonical order.
- A thin region that fails any gate (speck, confidence, mid-surface validation) falls back to **volumetric, never to sheet**. The mid-surface ladder's local re-triangulation rung is deferred to G7; today an invalid candidate goes straight to the volumetric fallback.
- Under the frozen coupling rule oscillation is unreachable through the constraint (`h` is a running minimum and Rule S3-M pins `t_r`), so each region changes regime at most twice. The oscillation guard covers hysteresis-boundary noise only; its test drives it through an inverted dead band.
- **An escalated cell's pieces must have their ownership *settled*, never inherited.** A cell straddling a surface carries `Ambiguous` for it; `resolve()` drops `Ambiguous` entries (its own doc says "S10 must refuse a record that still carries one"), so a piece that inherits the parent record resolves to `{0}` and its material goes to **background**. Until 2026-08-07 every escalated piece did exactly that. `seed_record` settles them by a `SPEC_meshgen_geometry.md` §7.5 interior sample instead. The symptom was 521 faces on A-3 between region key `{1,2}` and `{0}` - impossible, since the lens of two intersecting solids is interior to both - with the whole suite green.
- **A straight sharp edge and an intersection curve bend by zero, so no chord rule can see them.** `curvature_sources` and `feature_sources` measure bending; a cube edge is straight and two transversally crossing surfaces have no curvature. Before `curve_sources` existed, five of seven acceptance cases reported `geometry sources: 0 total` while S1 reported 12-24 curves, and A-8 reported 0 feature-curve sources against 180 sharp curves. The comment in `feature_sources` claiming "the mesh conforms to them through S7/S8 rather than by refining near them" was false of the implementation: S7 only snaps nodes already within `0.30 * l_min` of a curve, and S8 refuses to cut a cell two patches cross.
- **`t_sheet` and `t_layer` are fractions of the *converged* `h`, not of `h_max`.** Any criterion that lowers `h` narrows the thin-regime windows under whatever fixture is being aimed at them - `curve_cells = 2` halves the sheet window. - **§7.3's `FaceTriCache` landed as a kernel (`src/meshgen/facecache.rs`), and the crease needs a HUB on the face, not a chord.** Two patches of one component leave one chord each on a shared face, and they meet where the crease pierces it. - **Winding-independence is the J1 test that actually bites.** Two cells walk a shared face in opposite directions, so any face rule that reads the walk as given satisfies J1 on paper and cracks the mesh — which is precisely how the cell-local CDT integration failed. `canonical_walk` rotates to the smallest key and picks the direction whose *second* node is smaller, both functions of node keys alone. Count the four buckets exhaustively so they sum to the population; the interesting result was the bucket nobody had named being 94 % of it.
- **A conforming failure is worth far more than a non-conforming one, and it is worth engineering for.** The escalation trigger lost 1.2 points on a8 — and kept `[V1]`/`[V3]`/`[V9]` PASS on both cases it ran on. Because the mesh stayed intact, the loss was attributable to exactly one measurable thing: **58 % of the newly escalated cells (3,744 of 6,465) fell back to the chamfered centroid fan**. P-3.12's tracer lost on the same population three weeks of work earlier, but broke conformity while doing it, and the conformity failure masked the cause completely. **When a prototype is going to fail, prefer the version that fails with the invariants intact** — it is the difference between "this does not work" and "the delivery is right and the mesher behind it is wrong".
- **a8's defect is per COMPONENT, not per cell.** §6.14 counted *cells* with a fragment and no crossed edge (464). The real population is a **component** that enters a cell and crosses none of its six edges — which happens freely in a cell that another component *does* cut. `crossing_components` is built from `cut_index` over the edges, never sees the second component, so `crossing_components.len() > 1` stays false and no junction is declared. That population is **2,719 cells on a8, 5.9× the cell-level count**. Whenever a quantity is defined per cell, check whether the thing it is about is actually per component.
- **Factor, do not copy, when the duplicated code is a list of guards.** `subdivide_cell`'s body is five refusals, each added in response to a specific measured failure (the arena grew; a plane re-cut a shared boundary triangle; fewer than two pieces; a piece with under four faces). The fragment-driven entry point needs all five and differs only in where the planes come from, so the body moved into `subdivide_cell_by` and both entry points pass a closure. A second copy is exactly how one of those refusals goes quietly missing a year later.
- **Pin a refusal with a test that proves WHY it refuses.** `the_subcell_body_is_refused_until_the_face_carries_its_trace` asserts the wrapper declines, then cuts the *same cell with the same fragment* through the kernel directly and asserts that succeeds. Without the second half, the test is satisfied by a kernel that cannot cut at all, and the obvious "fix" when someone later wants the sub-cell body to pass is to weaken the guard. With it, the test says what the way out is.

- **A refusal that returns `None` is a dead end; a refusal that names itself is a work item.** `subdivide_cell`'s five guards all returned `None`, so a gate measuring 89 % refusals said only "it mostly does not apply". Changing the internal to `Result<_, &'static str>` — one line per guard — turned that into a histogram with the same shape on every case: **a8 86.0 %, a3 89.6 %, a6a 47.3 % is ONE reason**, *"the clip wanted a node the neighbour does not have"*, which is exactly what the three unwired face-side functions remove. The next step went from speculative-with-24-cells-behind-it to removing 86–90 % of every declined cell, on the strength of a mechanical change. It also **corrected a claim in the kernel's own test**: the sub-cell refusal test's comment blamed the shared-boundary check, and the guard that actually fires is one earlier.
- **The most informative case in a mesher swap is the one that does not move.** On a6a the fragment-driven kernel re-meshed 356 cells: the mesh file differs, the element count is *identical* (348,254), and the material boundary is identical to fifteen digits (0.995387032489948 both ways). That says the two mechanisms agree exactly about the geometry where both work and differ only in how they fill the interior — a far stronger statement than "the suite still passes", and it is the check that would catch a swap that quietly moves the boundary while improving the headline number.
- **Land it as the default when it measures strictly better; keep the handle only when it measures worse.** The fragment-driven cut is better on two cases, identical to the digit on seven, and costs 52 elements across the whole suite — so leaving it behind `RUSTMSPT_CDT_FRAG` would be precisely the correctness knob R3 forbids. The older `RUSTMSPT_CDT` handle stays a handle for the opposite reason: it was measured worse. **The gate is a statement about the measurement, not a permanent hedge.**
- **Measure-zero contact is not fragment, and the reason is that supporting planes are infinite.** A surface triangle meeting a lattice tet at one corner has no material inside it — but `planes_from_fragment` would still return its plane, and a plane cuts the *whole* cell. One tangent triangle doubles the piece count for nothing. The clip therefore keeps a triangle only when its intersection with the tet has positive area, measured in the cell's own units (`edge * 1e-6`, squared) rather than absolutely, so it means the same thing at every element size.

## Reporting to the owner (standing rule, set 2026-08-16)

Every substantial reply ends with a status block covering four things, in this order. It is not
optional and not conditional on the work having gone well.

1. **What finished** — the step just completed, with the numbers that say so.
2. **What is next** — the specific next step, not a direction. "Diagnose a8's 0.263 of off-surface
   area" is a next step; "keep improving P3" is not.
3. **Where things stand** — and this field has two forms, depending on whether the turn ends the
   work.

   *If stopping:* say why. Context exhaustion, a measurement that has to run, a decision that is
   the owner's, work genuinely finished, or a blocker — say which. Never let stopping look like
   completion, and never let completion look like stopping.

   *If not stopping:* report the **state**, not a reason. What is committed, what is verified, what
   is in flight. Do not answer the stopping question at all — a turn that continues has no stopping
   reason, and inventing one produces filler. "Commit boundary" was the filler this rule generated
   on six consecutive turns: literally true (tree coherent, tests green, default path unchanged) but
   answering a question nobody had asked, while the same reply said "I haven't stopped". If the
   honest content of this field is "I finished a unit of work and am starting the next", write that
   or write nothing.
4. **What I need from you, if anything** — a decision between named options with their trade-offs,
   or explicitly *nothing, proceeding*.

The reason this is a rule: several times the owner has had to ask "what's next?" after a reply that
reported results and then trailed off. A result without a next step reads as finished when it is
not, and the owner cannot tell the difference between "I ran out of room", "I need you to choose",
and "this phase is done" unless it is stated.

A crossing point on an edge is a pure function of that edge and the surface, so both incident cells derive it identically — the same property that made P-3.3's crease fan conforming. This is the highest-value unbuilt item, and it is a change to how the cap is placed rather than a new mesher.
- **P-3.9: §7.6's cap loops are clean — 0 of a8's 17,957 loop nodes sit outside the cut's own on-surface set.** So the cap is not being forced onto the lattice, and P-3.8's proposed fix (intern crossing points so the loop has somewhere on-surface to run) would give the loops somewhere to go that they already go. Withdrawn. It also settles what the offending faces are *not*: a cap triangle's corners are cycle nodes and every cycle node is in that set, while the structural residue's worst corners are lattice nodes measured as `constraint_kind` **free** — so **those faces are not cap triangles at all**. `[CAP-LOOP]` is kept: it is cheap and it is the check that would catch a future change pushing loops off the surface.
- **Eleven candidates are now closed on a8, each by measurement, and the mechanism is still open.** The population is: faces *inside* a §7.6-split parent, `provenance` 3, worst corner a **free** lattice node 0.4–0.7 h off the surface, face straddling it. Closed: the centroid fan, resolution, a lost edge crossing, the band path, hidden-solid recovery, the sub-cell labelling, the sub-cell body itself, the mixed-triangle relaxation, the face Steiner centroid, near-miss placement, and the cap loop's composition. **Every indirect route has been tried — the next step is to read one cell's full output, the way the sub-cell archetype was cracked, rather than to test another hypothesis from aggregates.**
- **P-3.10 — a8's mechanism, found by reading one cell after eleven indirect routes failed: a §7.6 PIECE that carries MIXED labels.** a8's parent 579166 has 16 tets in two fans; the fan with apex 226574 has **seven region-0 tets and three region-1**. A fan piece is supposed to carry one label, so the material boundary runs *inside the fan* along (apex, a, b) faces — and the offending `[V13]` face is exactly that, signed distances `[0.689, 0.399, −0.057]`. The piece was separated from its neighbour but **the surface still runs through it**; it was fanned to a centroid and its tets labelled individually by §7.5's interior sampling, so the boundary follows the fan out to a raw grid vertex two thirds of an element from the surface. **This project already had the general lesson — "coning a SPLIT piece to its centroid does not move the material boundary; coning an UNSPLIT one does" — recorded about whole cells (`[JCT-FALLBACK]`). Nobody had counted the case where a PIECE survives the split still straddling.**
- **When every hypothesis from aggregates has failed, dump one entity in full.** Eleven candidates were closed from suite-level metrics, each costing a build-and-measure cycle, and none found it. One `parent_cell` dump — 16 tets with their region keys — showed it immediately, exactly as the sub-cell archetype was cracked in P-4.4. **Aggregates tell you where to look; they do not tell you what you are looking at.**
- **P-3.11: more split passes do not help — §7.6 DECLINES on the straddling piece, it does not miss it.** The natural reading of P-3.10 was that §7.6 makes one pass per component, so a piece crossed *twice* survives it. Repeating each component's pass up to four times: a8 92.011 → **91.999**, a3 92.743 → 92.716, a6a identical. Nothing. a8's refusals, counted: **piece not split by component 289, one side empty 217**, a piece is not closed 76, inside holes are not simple loops 72. `split_soup_by_surface` needs the surface's trace to exist as **edges of the piece's boundary** before it can separate anything; where S7 recorded no crossing, the trace is not there. **The fix is to make the split succeed, not to run it again.**
- **The two open problems have converged on one capability.** The sub-cell body (a body passing through a cell touching no edge) and the mixed-label fan piece (a piece the split cannot separate because the trace is missing from its boundary) both need the same thing: **a cut driven by the surface fragment rather than by edge crossings** — SPEC §7.2's stated input. §7.6's decline reasons are the specification for what it must supply, and "one side empty" plus "piece not split by component" are 506 of a8's 654 refusals, both saying the trace is *missing* rather than malformed.
- **P-3.12: the boundary tracer was built to §7.6's decline reasons and fails at the CELL — for the fourth time, the trace must go in the FACE.** `trace_boundary_soup` split every straddling boundary triangle at a bisected crossing point, interned per **(edge, component)** in a map shared across cells. It fires (a8 826 triangles, a3 268) and is worse on every axis: **a8 92.011 → 91.756 with `[V1]` and `[V3]` both FAIL**, a3 92.743 → 91.630 with `[V3]` FAIL, and a8's `[JCT-FALLBACK]` rises **397 → 1000**. Two reasons, both instructive. (1) **`[V3]` breaks because the neighbour does not split** — a boundary triangle is shared and only the *escalated* cell runs the pre-pass, so the crossing node is a hanging node on the side that took §6's table. Sharing the map is not enough; **both cells have to reach the code**. (2) The split gets *less* successful, because changing the soup makes `fan_is_sound`, `cell_fan_is_conforming` and the cap guards reject more cells.
- **The corrected design is the one this project keeps rediscovering: start at the face.** The trace belongs in the **face's own triangulation**, computed once from the face and consumed identically by both cells — §7.3's `FaceTriCache`, already authoritative for escalated cells' faces and already proven at 0 conflicts. P-3.3's notes, the cell-by-cell CDT integration, P-3.4 and now P-3.12 have each landed on this from a different direction. **Any future work at this site starts at `check_face_cache`, not at `split_escalated_cell`.**
- **P-3.12 has TWO obstacles and the second is the harder one.** The conformity failure has a known remedy — restrict the trace to faces all of whose owners escalated (P-3.3's proven condition, reaching ~60 % of a8's surface-adjacent shared faces), and let the face cache deliver it to both cells. **But the fallback rise is independent of conformity:** a8's `[JCT-FALLBACK]` went 397 → 1000 with the trace in place, because splitting a triangle changes the soup that `fan_is_sound`, `cell_fan_is_conforming`, `fan_cap`'s apex search and the volume guard all inspect. A perfectly conforming trace still hits that, and a cell that falls back is *chamfered* — worse than the mixed-label fan it was meant to replace. **The next attempt's first step is therefore a measurement, not a build: apply the trace, count the `[JCT-DIAG]` decline reasons, and see which guard rejects.** `fan_is_sound` means the trace is making degenerate triangles and should place crossings away from existing nodes; the volume guard or cap search means it is producing pieces §7.6 cannot fan at all, which needs a different decomposition. Those point at completely different fixes.
- **The tracer had a bug of its own, and finding it separated the two obstacles.** The one-pass version split only the triangles that *straddle* — but a neighbouring triangle sharing a cut edge does not straddle, so it never received the node, leaving a hanging node inside the cell's own soup. That was a8's 554 "outside holes are not simple loops". **Splitting every triangle that carries a crossing on one of its edges, straddling or not, removes them entirely (554 → 0)** and returns "piece not split by component" to baseline (892 → 290). So the split now succeeds where it was refusing. What remains is two independent obstacles, and they are now cleanly separated: `cell_fan_is_conforming` rejects **1,628** cells (a guard that fired on none before — a *new* question), and `[V3]` still fails because only the escalated cell runs the pre-pass (the inter-cell problem, untouched by the fix). **The face-first remedy addresses only the second; building it alone would land on the first with conformity intact and still no gain.**
- **When a fix makes things worse, check whether the fix is correct before concluding the approach is wrong.** The one-pass tracer's failure looked like evidence that tracing the boundary is a dead end. It was a bug in the tracer — and fixing it turned the dominant refusal from 554 to 0. Two of this session's earlier refutations (P-3.4, P-3.11) were genuine; this one was not, and the difference only showed up because the decline reasons were counted rather than the top-line number.
- **Obstacle 1 is now a single named guard message, on all 1,628 cells: *"a node lies inside a fan face it is not a vertex of"*.** A hanging node — but at the **fan** level, not the soup level. The two-pass tracer removed the soup-level ones (554 → 0) and these appeared in their place, which localises it precisely: the trace's nodes are consistent across the boundary triangles that carry them and *inconsistent with something constructed afterwards*. Only two things are built after the pre-pass runs — `fan_cap` over the cap loops, and the per-piece fans. **That is the next thing to chase, and it is one message in one guard rather than a class of failure.** The tracer that reproduces it is saved at `scratchpad/tracer.py` (it must not ship — it breaks `[V3]`).
- **Save a diagnostic patch to a file the moment it is worth re-running.** This tracer was written, reverted, and rewritten from scratch three times in one session because `git checkout` was used to revert it before it had ever been committed. A scratchpad `.py` that re-applies it costs nothing and would have saved two rebuilds.
- **Obstacle 1, narrowed again: the offending face is NOT a cap triangle.** `fan_cap` rejects an apex whose fan swallows a loop vertex *on an edge* but says nothing about a vertex strictly **inside** a fan triangle — exactly what `cell_fan_is_conforming` reports. Extending `fan_swallows_vertex` to reject interior containment is a **no-op on the default path** (a8/a3/a6a identical to the digit, 370 tests green) and leaves the traced count at **1,628, unchanged**. So the apex choice is not the cause; both the guard and the tracer were reverted. That leaves the **per-piece fan** faces `(centroid, a, b)`: a crossing node sits *on* a boundary edge, so it lies inside such a face only if some triangle still carries that edge **uncut** — the pre-pass missed a triangle. **Check the cap triangles first**: `split_escalated_cell` adds them to both pieces *after* the pre-pass runs, their edges span loop vertices, and nothing traces them.
- **Obstacle 1, chased to the end: the traced pieces are NOT STAR-SHAPED from their centroids.** Instrumenting the guard to name the offending face's origin reports the same on all **1,628**: the face has no cap-only node and the intruding node is not cap-only either — both are ordinary boundary nodes. So the fan face `(centroid, a, b)` passes through **another part of the piece's own boundary**. Not a missed split, not a guard to loosen: a centroid fan cannot mesh a piece that is not star-shaped, and **tracing adds nodes and detail, which makes pieces less star-shaped — so the fan's own precondition fails more often the better the trace gets.**
- **The three open problems are ONE problem: the centroid fan's limits.** (1) The sub-cell body needs a cut from the surface fragment rather than edge crossings. (2) The mixed-label fan piece needs the trace on its boundary so the split can separate it. (3) The traced piece is separable but the fan cannot mesh it. All three are answered by **SPEC §7.2's local PLC mesher** — input is the cell's tet, its clipped surface fragments and its curve segments, and it cones nothing to a centre. The kernel exists and is tested (`src/meshgen/cdt.rs`); what it has never had is the **fragment input**. That is no longer one capability among several — **it is the remaining capability**, and every other route into these problems is now closed with numbers.

### P-3.13, the local PLC mesher: what worked and what did not

**The one defect behind four symptoms.** *The cut is derived twice — once for the faces and once for
the interior — and only where the two happen to agree can a cell be meshed.* Four appearances:
§6.35 one point interned under two spellings; §6.39 rim membership re-derived per face instead of
read off the edge; §6.41 a subdivider clipping against §5.2's world while the faces are split by the
trace; §6.43 the facet's rim recomputed instead of adopted. **None was ever fixed by moving a
threshold.** When two parts of the mesher must agree about a geometric quantity, one of them owns it
and the other reads it — decide which, and say so at the site.

#### Edits that were right

- **Charge every defect to the path that emitted it.** A histogram of leaking faces against the arm
  that produced them ended rounds of guessing in one run: `0 table / 0 meshed / 464 fanned / 0
  escalated`. The all-zero rows are as valuable — the T-junction row coming back zero killed the
  obvious next hypothesis before it was built.
- **Measure a number *with units*, not a threshold sweep.** Three tolerance edits in a row changed
  nothing (leaks 464 → 466). What ended it was "how far outside the face, in the face's own
  barycentric coordinates" — −2.9 × 10⁻², three percent of the face. **An absolute tolerance on a
  relative question fails completely below one scale and not at all above it, which is exactly why
  sweeping it looks inert.**
- **Name the refusal, then split the name when it covers two things.** "The boundary is not the
  frozen one" became combinatorial vs structural (§6.36), then structural in *both directions*
  (§6.42), then facet-edge vs facet-interior (§6.44). Each split turned an unexplained population
  into a work item, and twice the two halves needed completely different machinery.
- **Ask the refusal in both directions.** §6.36 measured "2,028 combinatorial, 0 structural" and it
  was true and half the question. *A node the hull carries that the boundary has never heard of* was
  never asked, and it was 72 % of the population.
- **Guard before the fan, not after it.** The fan checks nothing, so whatever it is handed becomes
  the cell. Three guards were needed to keep a split conforming and the *first two changed nothing*
  — which was the measurement that located the third (dropped degenerate cone tets).
- **Seed a bounded domain with the domain.** The face triangulator's super-triangle sat at 1000 ×
  the span while sliver circumcircles reach 10⁵ × it, so `retain` deleted a whole strip. Every point
  is already checked to lie inside the face, so **the face is the convex hull and coverage holds by
  construction.**
- **Make membership a lookup, not a predicate on 10⁻¹⁹.** Whether a point splits an edge is a
  property *of the edge*; two faces re-deriving it from `orient2d` project along different axes and
  decide differently, and the boundary cracks.
- **A constraint that runs through a vertex is two constraints** — in 3D as well as 2D. Applied to
  face constraints since §6.32 and not to facets until §6.44, where recovering a facet edge
  *created* it across a split point and put back 33 hanging nodes.
- **Build the dataset when the same guess keeps failing.** Six build-measure-revert cycles ended
  when one CSV of per-cell facts (`RUSTMSPT_PLC_CSV`, gated, print-only) plus pandas showed the
  decline rate rising 0 % → 100 % with fragment size and *flat* against cell shape. **Aggregates
  told us where to look; the per-entity dump told us what we were looking at.**

#### Edits that were wrong, and what the cost was

- **`edge × 0.5` as a match tolerance.** It worked and was indefensible — half an element is a
  relocation, not a coincidence. The right bound was `eps`, *because that is exactly how far the
  face had already moved its own points*. **A tolerance is defensible when you can name the thing it
  is measuring; if the only argument is "it works", it is a knob.**
- **Trusting a parameter's name.** `plc_attempt`'s parameter called `quantum` is passed
  `order_quantum`, a millionth of `eps`, so bounding a *coincidence* test by it did nothing at all
  — §6.35's category error a second time, in the same function, through a name. **Check what a
  tolerance parameter is actually passed at the call site before reasoning about its size.**
- **Reporting a correlation without its base rate.** A face-interior point raises the decline rate
  six-fold, which looks like the answer until you notice 1,614 of 2,253 declines have no such point
  at all.
- **Measuring the wrong function.** The first rim census used `fragment_in_cell`, which returns the
  **original** triangles — its own note says so — and read rim points 85 × the cell's edge away.
  Only the impossibility of that number caught it. **A number that cannot be true is a gift; the
  same error in a plausible range would have been believed.**
- **Fixing the symptom one level below the cause.** §6.41 tagged the fan's caps: 503 → 494. The
  violations were not in the cells the split reached but in the 473 it could not, and the split's own
  caps ignored the augmented boundary — the same root cause arriving from another direction.
- **Two snaps of fragment vertices to the arena**, at `edge × 10⁻⁹` and at `eps` six orders coarser:
  no change either time. The coarse one failing too is what ruled out the whole class rather than one
  threshold. **When a tolerance change is inert at two scales that differ by six orders, the
  mechanism is not a tolerance.**
- **Assuming a baseline.** "The default path passes everything" was true of a6a and never of a3,
  which already fails `[V2]` with 19 duplicate nodes and `[V6]`. Read a case's own baseline before
  charging a regression to a change.

#### Rules that keep paying

- **State the falsifier with the plan, then hold to it.** §6.42's item 1 was written as "if the
  hull-extra class does not collapse this is not the fix, whatever the acceptance number does". It
  collapsed 96 % and 99 %, so the acceptance gain was earned rather than coincidental.
- **A change that changes nothing does not stay** — unless it is a guard the other half of the code
  already carries, in which case keep it and **record it as neutral rather than sell it as a fix**
  (the 2D cavity flood, the max-min retriangulation).
- **Conformity is not tradeable.** Two changes in this stretch bought acceptance and broke `[V3]`;
  both came out. R1 permits no fallback that abandons conformity, and 2 % of one verifier is not an
  exception.
- **A proxy that improves while the goal degrades is not a proxy.** P-3.13 measured itself for eight steps on "cells §7.4 takes" (93.8 % → 98.8 %) and "tets per cell against the fan's 15–21". Neither is a goal property. Measured on the goals, the gated path is **3.2x worse on P3 for a6a, 2.0x for a3, and costs +38 % / +76 % elements on a3 / a1**. Split by region it improves near the curves and degrades an order of magnitude away from them — helping where it was built to help and hurting the ordinary cells a widened triage handed it. **Re-measure the goal properties every few steps, not the acceptance rate of your own offer.**
- **Three consecutive "the same trade as before" notes are an alarm, not a record.** `[V1]` went 3 → 7 → 19 → 20 across four steps, each dismissed by pointing at the previous step's identical dismissal. Nobody added them up. **When a cost recurs, quote its cumulative value, not its increment.**
- **Fix a degeneracy at the source, and derive the bound from what will happen next.** Measured with the EXACT predicate at emit time, §7.4 produced *no* inverted tet — `[V1]` found sixteen in the written file, so they are tipped over downstream. The bound that works is therefore not "can I compute this volume" (`orient3d_filtered`'s own error bound reached only 20 → 16) but "will this orientation survive a node moving": volume below `longest² × tol` means a height under `tol`. That took `[V1]` to **0 on both cases for 88 and 56 declined cells**.
- **A diagnostic must use the check's own arithmetic.** The in-cut inverted-tet census used a cross-and-dot in double and reported **zero** in a run where `[V1]`, which uses the exact `orient3d`, found sixteen. The two disagree precisely in the regime the census was about. **If you are charging a verifier's failures to a path, compute the verifier's quantity, not one that agrees with it in the easy cases.**
- **Run every case through a new path before believing any of it.** a1 had never once been run through the gated mesher. It passes *every* verifier — the only case that does — and costs **76 % more elements**, at 16.87 tets per taken cell against the fan's 14.97. On a1 the new kernel is more expensive than the construction it replaces; on a6a it is three times cheaper. **One case's ratio is not the kernel's ratio.**
- **Charge the GOAL to the path, not just the defects.** Every cause in P-3.13 was found by histogramming a defect against the arm that produced it — and P3, the property the project exists for, had never been charged to anything. One run: §7.4-meshed carries **0.0 %** off-surface area across 51,591 interface faces on a6a; §7.4-**fanned** carries **71.7 % of its own arm and 99.4 % of all off-surface area** from 2,109 faces. a3 agrees (0.4 % vs 86.9 % / 94.9 %). **The kernel was never the problem; the fallback was.**
- **That overturned the previous step's reading, which had been written up as a finding.** §6.45 concluded §7.4 "hurts the ordinary cells a widened triage hands it". It does the opposite — its output is better than §6's table. The region split (worse away from curves) was real and the *explanation* attached to it was invented. **A split that separates two populations tells you where, not why; charging it to the producing path tells you why.**
- **Convert a count into the quantity you care about before prioritising.** A fanned interface face carries 2.16e-6 of off-surface area against a meshed face's 5.4e-10 — a factor of **four thousand**. 519 declining cells produce 99.4 % of a6a's P3 damage. Ranking decline classes by cell count would have aimed the work at the wrong one; ranking by stranded interface area is the right order.
- **A conforming refusal is the correct fallback and a poor destination.** Refusing a cell is always safe and never free: on this path each refusal hands a cell to a construction four thousand times worse for the goal. **Prefer removing the offending element to declining the cell that contains it, and when you do decline, price it.**
- **Rank work by the quantity you care about, not by the count of things in each class.** On a6a the decline classes ranked by *cells* put "a facet's interior is not covered" first (220) and "a tet is thinner than the node quantum" fourth (88). Ranked by the **P3 area each strands**, the thin-tet class is **first at 47.6 %** and the facet class third at 11.6 %. The two orderings disagree completely, and the count ordering would have aimed a week at the wrong class.
- **Act on your own caution or delete it.** §6.46 wrote "a conforming refusal is the correct fallback and a poor destination" and then moved on; one step later that exact refusal was measured as the single largest source of stranded P3 area on the case. **A caution recorded and not acted on is a defect with a paper trail.**
- **Remove the offending element, do not decline the cell that contains it.** Refusing one unusable tet hands the whole cell to a construction four thousand times worse for the goal. Removing the tet by the same edge-removal machinery already present took the class from 88 cells to 40, its stranded share from 47.6 % to 14.6 %, and the case's total off-surface area down **36 %** — with `[V1]` still zero and `[V3]` still clean.
- **A user looking at a picture is running a check you did not write.** "a3's edge looks bad, a1 is not smooth" separated into one real structural defect and one benign resolution limit — a3's cube is a 12-triangle STL so every serration is the mesher's, while a1's is a 1,280-facet input at element size, already known to read 100.000 % at a quarter-element tolerance. **Render the result and look at it; the eye finds populations that aggregates average away.**
- **A tool defect I invented, and the cost of not checking it.** `color_by: region_key` was written off as "per-triangle rainbow noise, unusable" from one glance, and the nine report images were rendered in a single uniform colour as a result — which hid a4's nested cube entirely and prompted "I don't see the cube inside the sphere". The renderer was correct all along. `region_key = -1` is the *not-applicable sentinel for non-tet cells* — the tagged interface faces and rim lines in the same document — and `show_faces` defaults to **true**, so those faces were being drawn over the volume in sentinel colour. `show_faces: false` gives one clean colour per material. **Before recording a tool as broken, count the distinct outputs it produced; two dominant colours and a shading tail is not noise.**
- **"I can't see X" is a hypothesis about the picture, not about the mesh — check the data first.** a4's cube is 39,132 cells with a meshed volume of 0.013246 against an input 0.013245. The mesh was right and the visualisation was wrong, and confirming that took one query against the VTU.
